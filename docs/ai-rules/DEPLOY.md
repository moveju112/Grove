# 빌드·통합·배포

빌드 성공, 서비스 준비, 브라우저 접속, 인증된 기능 동작은 서로 다른 완료 조건이다.
소스 편집 요청을 commit·push·배포·서비스 중단 승인으로 확대하지 않는다.

## 빌드 잠금과 스냅샷

모든 세션의 편집 원본은 `/data/project/paseodog_opus`의 `main`이다. 최종 컴파일 요청은 아래 순서로 조정 담당 한 세션이 처리한다.

1. **접수·새 편집 대기:** 빌드 요청을 공유 상태에 등록하고 새 작업·새 파일 소유권 취득·완료된 작업의 편집 재개를 막는다. 이미 수정 중인 세션만 등록한 범위를 완료할 수 있다. 별도 세션이 동시에 다른 배포 후보를 만들거나 반영하지 않는다.
2. **진행 중 작업 완료 확인:** 모든 수정 중 세션의 완료와 쓰기 프로세스 종료를 확인한다. 단순 Git diff 부재, 일정 시간 대기, 세션 무응답으로 대신하지 않는다. 부분 변경·차단된 작업이 남으면 원본을 보존하고 빌드도 대기한다. 임의 timeout으로 누락시키지 않는다. 일부 변경 제외·작업 중단은 영향과 대상을 설명하고 사용자의 결정을 받는다.
3. **편집 잠금 확정:** 확인과 스냅샷 생성 사이에 새 쓰기가 끼어들지 못하게 잠금을 유지한다. 공유 상태·원자적 잠금 도구가 없다면 조정 담당의 명시적 동결 요청에 모든 소유 세션이 쓰기 중단을 확인한 뒤 진행한다. 확인할 수 없으면 컴파일을 시작하지 않는다.
4. **소스 스냅샷 고정:** 유일한 임시 경로를 할당해 main의 완료된 실제 소스를 고정한다. 완료된 미커밋 수정·새 소스 파일도 포함하며 Git HEAD만 내보내서 빠뜨리지 않는다. 기준 커밋, 포함된 세션·변경 범위, 실제 소스 입력 hash로 후보를 식별한다. 커밋·push 권한은 별도로 확인하며 스냅샷 생성을 이유로 자동 커밋하지 않는다.
5. **편집 재개·스냅샷 검증:** 복사 완료와 입력 hash 일치를 확인한 뒤에만 원본 편집 잠금을 해제한다. 이후 시작한 변경은 다음 반영 대상으로 공유 상태에 구분한다. 후보의 소스는 수정하지 않고, 검증·컴파일·패키징은 같은 스냅샷에서 수행한다. 후보 수정이 필요하면 main에서 수정한 후 새 동결 절차로 새 후보를 만든다.
6. **후보 반영·종료:** 배포 승인이 있으면 검증한 그 산출물만 반영한다. 후보 간 반영은 직렬화하고 이전 후보가 새 후보를 덮어쓰지 못하게 한다. 실제 실행 파일·웹 자산·CLI 진입 경로가 후보와 일치하고 필요한 인증 기능이 동작하는지 확인한 뒤 빌드·반영 상태를 종료한다.

위 절차는 운영 규칙이며, 이 문서 작성만으로 세션 상태 등록·편집 잠금·스냅샷 자동화가 구현되거나 기존 세션에 강제 적용되지는 않는다. 도구가 강제하지 못하는 단계는 위의 수동 조정 절차로 확인한다.

## 통합 검증과 완료 기준

- **MUST** 배포 대상은 기준 커밋·실제 소스 입력·패키지 hash로 확정하고 다른 세션의 미완성 변경을 포함하지 않는다.
  - why: 커밋이 같아도 공유 작업 폴더의 미커밋 변경과 별도 CLI 산출물이 다를 수 있다.
  - ✅ 모든 완료된 반영 대상이 스냅샷에 포함됐는지 대조하고 source/input hash와 receipt를 같은 후보에 결합한다. `evidence: scripts/build.py`.
- **MUST** 관련 변경은 통합 후보에서 묶어 빌드·인수하고 유효한 세부 검사 근거는 재사용한다.
  - why: 통합 검사를 반복하면서도 최종 기능 간 충돌은 놓치는 상황을 피한다.
  - ✅ 선택 Rust·Vitest·E2E 대상을 한 호출에 나열한다. `evidence: scripts/build.py`.
- **MUST** 같은 요구사항이 서버·웹·CLI에 걸쳐 있으면 모든 관련 구현과 실제 설치 경로에서 계약이 일치하는지 확인한다.
  - 최소 길이·권한·만료 같은 조건은 변경된 경계값의 허용·거절을 검사한다. 도움말 출력·연결 성공·기존의 긴 입력 성공만으로 조건 변경을 검증했다고 하지 않는다.
  - 소스 수정, 통합, 컴파일, 설치, 실제 기능 확인은 구분해 보고한다. 확정 후보에 포함됐는지 확인하지 않고 “다음 빌드에 자동 포함” 또는 “반영 완료”라고 안내하지 않는다.
- **MUST** 실사용 업데이트는 패키지 검증·서명된 manifest·기존 updater 경로를 사용한다.
  - why: 설치를 직접 덮어쓰면 검증 실패 때 이전 서비스로 복구할 수 없다.
  - ✅ package → signed manifest → `grove update apply`. `evidence: scripts/deploy_local.py`.
- **MUST** 실행 중 작업으로 적용이 `deferred`되면 성공 배포로 보고하지 않는다.
  - why: 패키지 준비와 실제 전환은 다르다.
  - ✅ readiness·적용 상태와 운영 release를 확인한다. `evidence: src/update.rs:754`, `evidence: scripts/deploy_local.py:165`.
- **MUST** 실패 복구에서 새 DB 쓰기를 과거 snapshot으로 덮어쓰지 않는다.
  - why: 이전 release 복구가 데이터 유실을 일으켜서는 안 된다.
  - ✅ `Recovery` 판정과 `recovery_never_overwrites_new_writes` 시험. `evidence: src/update.rs:884`, `evidence: src/update.rs:1170`.

|---|---|
| 패키지 준비·자체 실행 검증 | `python3 scripts/build.py package --targets linux-x64` |
| 실사용 상태만 조회 | `python3 scripts/deploy_local.py --status` |
| 승인된 로컬 설치·업데이트 | `python3 scripts/deploy_local.py` |

고정 포트·unit·경로는 `scripts/deploy_local.py`를 정본으로 삼는다.
공개 웹 배포 성공을 로컬 daemon 업데이트 성공으로 대신 보고하지 않는다.
