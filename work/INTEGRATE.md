# 메인 세션 진입: 완료 작업 통합 → 검증 → 정리 → 다음 작업 준비

## 역할과 시작
이 문서는 원본 프로젝트의 메인 세션에서 실행하는 통합 절차다. 사용자가 “00 메인 세션”이라고 부르는 세션이나 다른 메인 세션에서도 사용할 수 있다.
메인 역할은 실제 Git top-level·브랜치와 사용자 요청으로 판별한다. 기존 00 기능 worktree(`parallel/b01-source-settings`)는 원본 설정 담당이며, 이름이 00이라는 이유로 통합 역할을 맡거나 작업 위치를 자동 전환하지 않는다.
사용자가 통합·합치기·정리·다음 작업 준비 중 하나라도 요청하면 이 절차 전체를 실행한다. “정리해줘”, “합쳐줘”, “10개 뽑아줘”만 보내도 1~5단계를 모두 수행한다. 사용자가 명시적으로 뺀 단계만 생략한다. 문서 조회·작성 요청만으로는 실제 통합이나 삭제를 시작하지 않는다.
통합 대상 프로젝트는 `/data/project/paseodog_opus`, 대상 브랜치는 `master`다.
현재 작업 위치와 Git root·브랜치를 확인한다. 기능 worktree에서 이 절차를 실행하지 않는다.
적용되는 공통·프로젝트 룰, `work/README.md`, `work/COMMON.md`, 해당 번호 문서를 읽는다.
같은 통합 checkout의 편집 담당은 한 세션이어야 한다. 다른 통합 세션이 작업 중이면 함께 편집하지 않는다.
현재 미커밋 변경은 소유권과 인계 범위를 확인한다. 남의 변경을 포함하거나 stash/reset/restore/clean하지 않는다.
상태는 파일과 Git·Paseo 실제 상태로 복구한다. 이전 대화를 반드시 읽거나 사용자에게 작업 결과를 복사해 오도록 요구하지 않는다.

## 권한 범위
위 실행 요청은 START의 통합 프롬프트와 같은 범위를 승인한 것으로 처리한다. 사용자에게 긴 프롬프트를 다시 보내게 하지 않는다:
- 완료한 배치 작업의 로컬 merge, 필요한 연결·결함 수정, 검사와 관련 로컬 커밋.
- 검증·TODO 반영·보존 조건을 모두 충족한 정확한 작업 worktree와 Paseo 워크스페이스의 정리.
- 최신 통합 커밋에서 다음 독립 기능의 문서·브랜치·worktree·Paseo 워크스페이스 준비.
push·배포·의존성 추가/업그레이드·운영 서비스 중단·강제 삭제·이력 재작성·작업 브랜치 삭제는 포함하지 않는다.
기본은 사용자가 각 워크스페이스에서 공통 프롬프트로 직접 시작한다. 사용자가 생성·프롬프트 전송·완료 감지·병합·정리·TODO 반영의 자동 반복을 명시적으로 승인한 경우에만 아래 자동 순환 계약을 적용한다.

## 1. 완료 작업만 수집
README의 활성 목록에서 실제 경로·브랜치·workspace ID를 확인한다. 세션 목록은 프로젝트 한 곳으로 제한되지 않도록 서비스의 전체 목록 또는 정확한 workspace 조회를 사용한다.
첫 수집은 `python3 scripts/integration_queue.py --root /data/project/paseodog_opus --max-running 10 --events /home/ubuntu/.cache/grove-events/events.jsonl`로 수행한다. 사용자 최신 명시 설정의 운영 상한을 명시하며 점검기 기본값 4는 바꾸지 않는다. 옵션은 1..10만 허용하고 기존 초과 실행을 중단하지 않는다. 한 번의 전체 세션 조회와 Git worktree 목록으로 `prepared`, `running`, 완료 후보·계속할 작업·blocker·과거 인계 검토를 구분한다. 점검기는 이벤트 append 외에는 읽기 전용이며 종료 세션의 committed RESULT 앞 8 KiB 완료 계약만 읽는다. 실행 중인 worktree의 RESULT·diff·검사 로그는 읽거나 세션을 시작하지 않는다.
`candidate`는 clean·종료 상태·committed RESULT가 있는 통합 후보일 뿐 완료 승인이 아니다. `integrated-candidate`도 ancestry만 확인했으므로 검증·TODO·정리는 별도다. `prepared`도 기준 SHA·정확한 workspace·승인 조건을 확인하기 전에는 시작하지 않는다. 조회 실패는 빈 큐로 간주하지 않는다.
`needs-continuation`은 맡은 범위의 실행 가능한 잔여가 남은 종료 세션이다. `blocked`는 해제 조건이 명시된 실제 외부 blocker이고 무한 재개하지 않는다. `legacy-review`는 과거 인계를 한 번 읽고 실제 잔여·승인·검사 대기를 분류할 대상으로서, 완료나 자동 재개로 추정하지 않는다. 잘못된 완료 계약은 `invalid-handoff`로 보존한다.
기능 세션의 소유 범위에서 해결 가능한 잔여를 메인이 재구현하거나 다음 번호로 계속 떠넘기지 않는다. 단일 소유권·현재 상태·실행 슬롯을 확인한 뒤 원래 종료 세션에서 이어가도록 하고, 정확한 종료 조건과 필요한 연결 소유권을 전달한다. 기존 진행 세션·기준 SHA·유효 검사는 보존한다. 실제 외부 blocker는 이유·해제 조건을 TODO와 이월에 남기고 독립 작업을 계속한다.
새 후보와 기능 tip·세션 상태·완료 계약이 바뀐 항목의 `work/RESULT-NN.md`, 커밋, diff와 검사 근거만 깊게 확인한다. 통합 HEAD만 바뀌었으면 ancestry와 실제로 영향받은 공통 입력을 확인하며 모든 인계를 다시 읽지 않는다. 입력이 같은 기존 조사·검사 근거는 재사용한다. 상태 변경 직전에는 정확한 대상의 세션·권한 대기·clean·tip을 다시 확인한다.
대상 세션이 running/initializing이거나 인계가 없거나 미커밋 변경이 남으면 통합·삭제 대상에서 제외한다.
idle만으로 완료라고 추정하지 않는다. 인계 파일의 완료·중단 상태 및 실제 코드와 대조한다.
소유 범위를 끝내고 종료·RESULT·커밋·clean이 확인된 작업은 이번 통합 대상이다. `needs-work`는 완료로 수집하지 않고 원래 담당의 이어하기로 돌린다. 실제 외부 blocker만 남은 부분 구현을 보존 목적으로 합칠 때도 TODO를 완료로 바꾸지 않는다. 통합 대상에서 제외해야 하면 담당·다음 동작 또는 해제 조건을 기록한다.
진행 중인 다른 worktree의 기준이나 작업 문서는 바꾸지 않는다.
취소한 06은 대상에서 제외한다.

## 2. 순차 통합·필수 검증
이미 대상 브랜치에 포함된 커밋은 다시 합치지 않는다.
일반 merge를 우선해 작업 커밋의 ancestry를 보존한다. squash/cherry-pick으로 정리 조건을 복잡하게 만들지 않는다.
권장 순서와 실제 의존성에 따라 하나씩 합친다. 의미 충돌을 한쪽 내용으로 기계적으로 덮지 않는다.
관련 후보 2~3개를 하나의 검증 묶음으로 처리한다. 모든 완료 후보는 같은 운영 흐름에서 순서대로 처리하되 기능마다 같은 서버·웹 빌드와 E2E를 반복하지 않는다. 후보가 하나뿐이면 수를 채우려고 기다리지 않는다.
공통 API·도구 등록·runner·화면 연결을 완성하고 사용자 흐름을 확인한다.
기능 담당이 미실행한 컴파일·타입·브라우저 검사를 반드시 수행한다. 입력이 유효한 기존 통과 근거는 재사용한다.
독립 기능의 정확한 선택 E2E는 번호 문서와 후속 지시로 기능 workspace에 맡길 수 있다. 작업자는 같은 공유 잠금 아래 빌드부터 브라우저 종료까지 실행하고 자기 결함을 수정한다. 통합 담당은 해당 근거의 입력을 대조해 재사용하고 공통 의미 경계·통합으로 영향받은 회귀만 추가한다. 기능별 E2E를 맡겼다는 이유로 최종 통합 인수를 생략하지 않는다.
묶음의 연결 변경이 안정된 뒤 필요한 Rust target·Vitest 파일·typecheck·E2E spec을 선택 검사 한 호출에 합친다. 성공 근거의 관련 입력이 유지된 검사는 제외할 수 있지만, 합쳐진 공통 계약의 검증이나 미실행 E2E를 생략하지 않는다.
Rust·웹 빌드·E2E는 기본 순차 실행한다. 메인을 포함한 모든 E2E는 `flock /home/ubuntu/.cache/grove-rust-check.lock python3 scripts/build.py test --e2e ...`로 전체 명령을 감싸고, 잠금 밖에서 이미 실행 중인 E2E가 없는지도 확인한다.
긴 검사는 아래 고정 candidate 검증으로 분리한다. 원본 checkout에서 이미 실행 중인 검사는 취소·이동하지 않으며 기존 입력 불변 계약을 유지한다. 검증 전 HEAD에서 신규 기능을 분기하거나 시작하지 않는다.
실패·timeout·미실행을 숨기지 않는다. 실패 수정 뒤 영향받은 검사만 재실행한다.
의미 있는 재설계·새 승인 요구가 있으면 해당 작업의 정리를 보류하고 독립 작업은 계속한다.
코드가 main에 들어갔다는 이유만으로 검증 완료·제품 기능 완료로 보고하지 않는다.

### 고정 candidate 비동기 검증과 실패 격리
- 첫 단계에서는 메인이 유일한 병합 작성자다. 실행기는 merge·커밋·TODO 완료·정리·세션 재개를 하지 않는다.
- 관련 묶음의 입력을 커밋으로 확정한 뒤 `python3 scripts/integration_validation.py run --root /data/project/paseodog_opus --candidate <정확한-SHA> --store /home/ubuntu/.cache/grove-validation --timeout 3600 -- --e2e <선택-spec>`를 background task로 실행한다. 승인된 공통 빌드 환경을 먼저 적용하고 선택 옵션은 기존 build.py 계약을 따른다. 원본 미커밋 변경은 candidate에 포함되지 않는다.
- 실행기는 고유 job 아래 독립 Git clone을 만들고 candidate를 detached checkout한다. 원본 index·HEAD·worktree 등록을 변경하지 않는다. `.dev`와 `web/node_modules`는 원본 공유 환경을 연결하고 설치하지 않는다. 공유 dependency·툴체인·cache 설정은 검사 중 변경하지 않는다. Rust·E2E 공유 잠금은 그대로 유지하므로 병렬 E2E를 허용하는 변경이 아니다.
- 시작 출력의 job 경로를 보존하고 완료 알림을 이용한다. `inspect --root /data/project/paseodog_opus <job>`로 최종 상태·선택 범위·SHA·원래 종료 코드를 읽는다. `output.log`에 전체 출력을 남긴다. 실패·timeout·중단 job은 덮어쓰거나 성공으로 바꾸지 않는다. 반복 polling·동일 입력 재실행은 하지 않는다. 프로세스 강제 종료로 마지막 상태가 running인 경우 완료로 추정하지 않는다.
- 고정 checkout 검증 중 메인은 다른 후보 조사·소유권 보완·승인된 기존 세션 이어하기·독립 통합을 진행할 수 있다. 검사 checkout과 공유 환경은 수정하지 않는다. 기존 원본 검사와 달리 원본 HEAD 변경은 고정 검사 입력을 바꾸지 않는다.
- `reusable=true`는 현재 원본이 clean이고 정확히 검증 SHA일 때만 반환한다. 이는 해당 선택 검사 근거일 뿐 전체 인수 승인이 아니다. HEAD나 미커밋 입력이 달라지면 자동 재사용하지 않고 메인이 관련 입력 차이를 판단해 영향 검사만 수행한다.
- 실패는 job·기능·공통 경계별로 분류하고 원래 담당에게 좁은 결함 수정을 맡긴다. 의존성 없는 다른 후보는 계속 처리한다. 공통 인증·저장·복구·빌드 결함이면 영향받는 묶음을 보류한다. 실패한 후보가 포함된 HEAD에서 다른 검사가 통과해도 실패 항목을 완료 처리하지 않는다.
- job checkout·로그는 검증 근거와 복구를 위해 보존한다. 자동 삭제나 기능 workspace 목표 15개에 포함하지 않는다. 자동 병합과 검사 슬롯 증설은 별도 후속 범위다.

## 3. TODO와 인계 보존
### 사이클 계측
- 이벤트 저장소는 `/home/ubuntu/.cache/grove-events/events.jsonl`이다. 원문 대화·토큰·환경변수·명령 인자·개인 경로를 넣지 않는다. 모듈은 허용된 작업 번호·commit·검사 job ID·상태·이유 코드만 받아 0600 JSONL에 잠금 append한다. 기존 기록은 자동 삭제하지 않는다.
- 큐 호출에는 `--events /home/ubuntu/.cache/grove-events/events.jsonl`을 추가한다. `queue-observed`와 `workspace-observed`는 그 시각의 관측이며 실제 시작·완료 시각이 아니다. 첫 관측 이전의 시간을 역산하거나 과거 이벤트를 합성하지 않는다. 옵션이 없으면 기존 읽기 전용 동작을 유지한다.
- 고정 검증 `run`에도 같은 `--events`를 `--` 앞에 추가한다. 단일 기능이면 `--work NN`, 묶음이면 같은 job ID와 commit으로 각 작업의 인수 이벤트를 연결한다. 준비·공유 잠금 대기·실행·최종 상태 전이와 이전 단계의 monotonic duration을 자동 기록한다. `state.json`에도 `phase_seconds`가 남는다. telemetry_error가 있으면 시험 결과와 별도로 계측 누락을 보고한다.
- 실제 운영 경계에서 `python3 scripts/integration_events.py --events /home/ubuntu/.cache/grove-events/events.jsonl --event EVENT --work NN --commit FULL_SHA`를 호출한다. `assigned`, `prepared`, `start-requested`, `started`, `completion-observed`, `intake-started`, `merge-started`, `merge-finished`, `fix-requested`, `cleanup-finished`, `deferred`를 사용한다. merge 전후에는 `--before-commit FULL_SHA`, 검사 연결에는 `--job validation-ID`를 덧붙인다.
- 시작 요청 접수는 start-requested일 뿐 started가 아니다. started는 실제 running 확인, completion-observed는 종료 인계 확인, merge-finished는 실제 Git 결과, cleanup-finished는 정확한 정리 결과를 확인한 뒤 기록한다. deferred/fix-requested의 이유는 `capacity/backlog/shared-lock/dependency/approval/conflict/test-failure/environment/unknown` 중 하나만 쓰며 상세 원문은 넣지 않는다.
- 외부에서 수행한 배정·병합·정리의 기록 호출은 메인이 맡는다. 로그 파일 자체가 자동화 권한·성공 판정을 부여하지 않는다. 순환 누락을 찾는 완료 알림·heartbeat에서 누락 상태를 확인하되 중복 실행하지 않는다.
- 이미 실행 중인 검사는 변경·재시작하지 않는다. 개발 workspace의 외부 flock 대기처럼 계측기를 거치지 않은 구간은 정확한 시간을 알 수 없다고 표시한다. 단계 duration과 관측 간격을 섞지 않는다.
- 강제 종료·기록 실패로 마지막 종료 이벤트가 없으면 성공이나 정확한 종료 시각을 추정하지 않는다.

TODO 항목별 전체 요구·필수 검증을 확인해 충족한 항목은 반드시 `[x]`와 근거를 반영한다.
부분 구현·필수 실기기/플랫폼 미검증은 `[ ]`로 남기고 실제 진척·남은 조건을 기록한다.
기능 세션이 종료됐다면 남은 연결·검증 때문에 worktree를 남기지 않는다. 통합 담당이 이번 흐름에서 끝낼 수 있는 연결은 끝낸다. 남은 연결·외부 검증은 `TODO.md`의 `[ ]`와 README의 “이월 작업” 표에 TODO ID·RESULT 경로·남은 조건으로 기록한 뒤 정리한다.
작업자가 결함을 직접 고쳐야 해 같은 세션을 재개할 때만 그 worktree를 보존한다.
해당 작업의 RESULT가 통합 checkout에서 읽히고 보존된 커밋에 포함돼 있는지 확인한다.
RESULT의 완료 SHA는 실제 작업 브랜치와 대조한다. 작업 결과 자체에 자기 커밋 SHA가 없으면 브랜치 tip을 기준으로 한다.
검증·TODO 변경을 승인된 로컬 커밋으로 남긴다. 무관한 미커밋 변경은 포함하지 않는다.

## 4. 정확한 완료 worktree·워크스페이스만 정리
각 대상에 대해 모두 확인한다:
1. 경로가 README에 기록된 작업 worktree이며 원본 프로젝트·HOME·루트가 아니다.
2. 해당 workspace ID의 실제 cwd가 그 경로와 일치한다.
3. 그 workspace 소속 에이전트가 모두 작업을 종료했고, 보존해야 할 다른 작업이 없다.
4. worktree가 tracked/untracked 변경 없이 깨끗하다. 미추적 파일을 disposable로 추정하지 않는다.
5. 작업 브랜치 tip이 검증한 통합 HEAD의 ancestor이고, 통합 후 추가 커밋이 없다.
6. RESULT·코드·검증 근거·TODO 상태가 통합 저장소에 보존돼 있다.
7. 해당 작업과 통합 영향 검사가 통과했다. 미해결 결함 때문에 작업을 재개해야 하는 상태가 아니다.

조건 하나라도 불충족이면 그 대상은 보존하고 이유를 보고한다. 강제 삭제하거나 실행 중 에이전트를 중단하지 않는다.
Paseo의 workspace archive 기능으로 정확한 ID만 정리한다. 이 작업은 종료된 소속 세션도 보관 처리하므로 그 영향을 함께 확인한다.
서비스가 worktree 디렉터리까지 제거했다고 응답하면 중복 삭제하지 않는다.
서비스가 디렉터리를 남겼다면 실제 Git worktree 등록과 상태를 다시 확인한 뒤 지원되는 관리 경로로 정확한 worktree만 제거한다.
일반 `rm -rf`, 광범위 glob, 강제 제거는 사용하지 않는다.
Git worktree 목록과 Paseo 활성 목록에서 제거됐는지 확인한다.
Paseo가 soft archive만 제공한다면 hard delete했다고 말하지 않는다. 사용자 화면의 활성 워크스페이스 제거와 디렉터리 제거를 구분해 보고한다.
작업 브랜치와 통합된 커밋은 복구 근거로 유지한다.

## 5. 빈 자리 자동 보충
정리 직후 같은 흐름에서 반드시 수행한다. 정리만 하고 끝내지 않는다. 건너뛰면 최종 보고에 이유를 쓴다.
준비 순서를 지킨다: ① 번호 문서와 README 활성 표 행(예정 경로 `/home/ubuntu/.local/share/paseodog/paseo/worktrees/0q796rug/<slug>`·브랜치)을 먼저 작성·커밋한다 → ② Paseo workspace를 만든다 → ③ 반환된 cwd·브랜치가 표와 같은지 확인하고, 다르면 표를 고쳐 커밋한다 → ④ 그 뒤에 사용자에게 알린다. workspace가 보이는데 표가 없으면 사용자가 먼저 시작한 세션이 매칭 실패로 멈춘다.
운영 목표는 활성 기능 worktree 15개다. 사용자가 개수를 바꾸면 그 값을 따른다.
이 수는 진행·준비 workspace 총수이며 동시 구현 수가 아니다. 새 시작·재개는 아래 실행 한도를 따른다. 슬롯이 없어도 준비 workspace를 지우거나 번호를 재사용하지 않는다.
새 배정 수는 목표 수에서 현재 남은 진행·준비 worktree 수를 뺀 값이다. 정리가 실패해 남은 worktree도 활성 수에 포함한다.
후보 우선순위: README 이월 작업 → 최신 TODO의 미배정 독립 사용자 흐름. 진행 중·이미 준비된 담당의 파일·API·의존성과 겹치지 않게 한다.
한 worktree 안에서 등록·화면·API 연결까지 끝내고 로컬에서 검증할 수 있는 흐름을 고른다. 모듈만 만들고 연결을 통합 담당에게 넘기는 분할은 하지 않는다. 실기기·원격 TLS·사용자 계정처럼 외부 조치가 필요한 검증만 남는 작업은 뒤로 미룬다.
TODO의 제외 결정과 사용자 제외 범위를 배정 전에 확인한다.
제외된 기능과 취소한 06을 되살리지 않는다. 새 기능을 임의로 늘리거나 미완료 세부 항목을 억지로 쪼개 수를 채우지 않는다.
새 번호는 준비·완료·취소 이력 전체의 최대 번호 다음부터 단조 증가시킨다. 다음 최초 번호는 10이다. 기존 번호를 재사용하지 않는다.
01~09가 진행 중이어도 새 작업은 최신 검증 통합 커밋에서 분기한다. 기존 작업의 기준은 그대로 유지한다.
정확한 소유 파일·입출력·권한·오류·복구·검증·통합 요구를 번호 문서에 확정하고 새 기준 SHA를 명시한다. 연결에 필요한 공통 파일의 정확한 연결 지점(예: `src/tools/mod.rs`의 등록 줄, 라우트 등록, 화면 mount 위치)도 소유 범위에 적는다.
배정 전에 실제 호출 경로에서 서버 라우트·도구 등록·runner·store/migration·화면 mount 중 필요한 지점을 확인한다. 구현·연결·선택 검사·자기 결함 수정·E2E 작성까지 담당 workspace에 묶는다. 공통 파일이라도 분리 가능한 연결 지점은 번호 문서에 지정한다. 같은 함수·migration 순서·상태 계약이 겹치면 함께 배정하거나 선행 작업 통합 뒤 배정한다. 소유권 때문에 핵심 연결을 메인에 넘기는 분할은 하지 않는다.
자기 변경에 국한된 결함은 인계된 재현·실패 로그·허용 경로를 원래 종료 세션에 전달해 수정하게 할 수 있다. 정확한 상태와 시작·재개 한도를 확인하고 소유권을 다시 지정한 경우에만 요청한다. 메인은 같은 범위를 동시에 고치지 않고 독립 작업을 진행한다. 실행 중·오류·취소·권한 대기 세션을 이 조항으로 재개하지 않으며, 공통 의미 충돌·통합 HEAD에서만 재현되는 결함은 통합 담당이 맡는다.
새 작업에 사전 승인이 필요한 의존성·외부 환경이 있으면 가능한 다른 작업을 우선한다. 독립 작업이 부족하면 적게 준비하고 이유를 보고한다.
새 브랜치·관리형 worktree·Paseo 워크스페이스를 만들고 실제 반환된 경로·ID를 README에 기록한다.
ENTRY/COMMON/START는 모든 번호가 같은 방식으로 시작하도록 유지한다. 파일 존재·경로·브랜치·소유권 겹침을 확인한다.
완료 작업의 문서와 RESULT는 보존하고 README의 활성 표에서만 완료 이력으로 옮긴다.
수동 운영에서는 기능 에이전트를 시작하지 않고 새 워크스페이스 이름·번호를 알려준다. 자동 순환 운영에서는 문서 커밋과 workspace 경로 검증을 마친 뒤 준비된 workspace의 세션을 시작한다.

## 중단 후 재실행
통합·검증·정리·새 준비의 실제 상태를 각각 확인해 미완료 단계부터 재개한다.
이미 archived/제거된 workspace는 다시 삭제하지 않는다.
정리 후 새 배정 전 중단됐다면 README의 완료 이력과 현재 활성 수를 확인해 남은 빈 자리만 보충한다.
같은 번호·브랜치·기능을 중복 생성하지 않는다.
검증 입력이 바뀌면 해당 근거는 재검증하고, 단지 세션이 바뀌었다는 이유로 모든 검사를 반복하지 않는다.

## 자동 점검(heartbeat)
사용자가 주기 점검을 켜면 매 점검은 위 읽기 전용 큐 수집부터 한다. 실행 중인 worktree는 상태만 확인하고, 새 종료 후보가 없으면 RESULT·diff·긴 TODO·과거 로그를 다시 읽지 않는다.
통합할 작업이 없으면 파일·Git을 바꾸지 않고 한 줄로 끝낸다. 자동 순환 운영의 미시작 작업은 아래 조건을 만족할 때 시작할 수 있다. 이미 확인한 진행 중 작업을 다시 깊게 조사하지 않는다.
이전 점검의 고정 candidate 검증이 진행 중이어도 heartbeat 전체를 건너뛰지 않는다. 같은 작업의 merge·검증·정리는 중복하지 않고 독립적인 큐 수집·승인 후속·유효 기준의 신규 슬롯 보충·다음 배정/의존성/선택 검증 준비만 진행한다. 원본 checkout의 검사가 진행 중이면 해당 소스·HEAD와 공유 환경을 보존한다. 완료 알림으로 인수를 재개하고 heartbeat는 누락을 복구한다.
Rust 검사는 기능 세션과 같은 잠금(`flock /home/ubuntu/.cache/grove-rust-check.lock ...`)으로 실행해 동시 빌드를 피한다.
진행 중인 기능 세션에 메시지를 보내거나 작업을 대신하지 않는다.

## 실행 한도와 backpressure
- 준비 workspace 목표는 15개다. 사용자 최신 명시 설정으로 신규 기능 시작·승인된 재개 후 실행 중·초기화 세션 합계는 최대 10개이며 `--max-running 10`을 명시한다. 점검기 기본값 4는 유지한다. 이전 준비 10개·실행 6개 제한 실험은 대체됐으며 이전 상한을 대기 이유로 쓰지 않는다. 상한 10은 항상 10개를 강제로 시작하라는 뜻이 아니다. 같은 기능 workspace의 여러 세션과 활성 표에서 누락된 등록 기능 worktree의 실행도 센다. 기존 초과분은 취소·중단하지 않고 자연 종료를 기다린다.
- 완료 후보와 통합 후 검증·정리 대기 후보가 합계 3개 이상이면 새 기능 시작보다 해당 검증 묶음을 우선한다. 큐의 `start_slots`는 사전 조사용 상한이지 실행 승인이 아니다. 시작·재개 직전에 최신 세션 상태·권한 대기·기존 작업 이력과 정확한 기준을 다시 확인하고 한 번에 하나씩 접수한다.
- 이미 맡은 기능의 검증된 idle 이어하기는 신규 기능 시작보다 우선한다. `continuation_slots`는 backlog와 별개로 총 실행 한도 안의 상한만 알려 준다. 이는 에러 재시도·취소 복구 승인이 아니며, 동일 blocker·동일 tip·같은 실패에 진척 없이 반복 재개하지 않는다. 운영 점검마다 계속할 담당·다음 동작 또는 실제 blocker가 있어야 하며 이유 없는 idle 방치는 허용하지 않는다.
- 기존 검사 잠금을 없애거나 Rust 빌드 수를 임의로 늘리지 않는다. E2E의 고정 포트 단일 실행과 workspace 관리의 순차 호출을 유지한다. 모델·effort·heartbeat 주기와 수량 목표는 이 최적화만으로 변경하지 않는다.
- 후보가 0이면 승인된 신규 슬롯 보충과 다음 배정·의존성·선택 검증 준비를 수행한다. 실제 권한·의존성·소유권 충돌·서비스 제한으로 실행할 수 없는 부분만 보류하고 이유를 남긴다. 공유 검사 잠금 대기는 구현 슬롯 한도와 구분하며 잠금을 풀거나 검사 병렬화로 우회하지 않는다. backlog 3개 이상 신규 시작 보류는 그대로 유지한다.
- 상한 10은 독립 구현을 겹쳐 진행하는 설정이지 Rust/E2E 검사 병렬화가 아니다. Rust target은 반복 옵션 대신 `--rust target1 target2`로 묶고 신규 배정·종료 후 승인된 재개에 전달한다. 툴체인 해석 수정은 다음 검사부터 사용하며 이미 실행 중인 검사·툴체인 설치·공유 환경을 변경하거나 취소하지 않는다.
- 단계별 대기·실행 시간은 기존 검사 출력과 서비스 시간 근거가 있는 경우만 비교한다. 완료→통합 대기와 공유 검사 잠금 대기를 구분한다. 일시 busy/running 수·CPU idle·가용 메모리만으로 효율 향상을 주장하지 않으며 swap 사용과 실제 대기/오류도 함께 관측한다. 측정 전에는 처리량 향상이나 절감률을 완료 사실로 보고하지 않는다.

## 실행 중 세션에 변경 적용
규칙 파일 수정만으로 기존 세션의 문맥·설정·예약 프롬프트가 갱신되지는 않는다. 변경을 맡은 세션은 별도 worktree에서 편집하고 통합 checkout 작성자에게 정확한 diff·검증 근거를 인계한다.
통합 담당은 안전한 작업 경계에서 원본에 반영된 AGENTS·INTEGRATE·COMMON·START를 읽고 새 운영 제약을 확인한다. 기존 heartbeat 진입도 최신 INTEGRATE를 읽도록 같은 대상의 기존 예약만 갱신하거나 기존 프롬프트의 재로딩 계약을 확인한다. 중복 예약이나 실행 중 검사 재시작을 만들지 않는다.
사용자가 실행 중 세션 적용을 명시한 이번 변경에 한해 기존 기능 세션에 한 번만 운영 변경을 전달할 수 있다. 번호 문서·기준 SHA·소유 경로·진행 중 작업과 유효한 검사는 보존하고, 다음 안전한 경계에서 메인의 COMMON을 읽게 한다. 새 작업을 시작하거나 소유권을 넓히거나 검사·구현을 처음부터 반복하게 하지 않는다. 일반 heartbeat의 개입 금지는 그대로 유지한다.
메시지 접수와 실제 재로딩 확인을 구분한다. 확인되지 않은 세션을 적용 완료로 보고하지 않는다.

## 자동 순환(사용자 명시 승인 시)
- 현재 사용자는 기능 세션 자동 시작과 반복 운영을 승인했고 최신 요청으로 목표를 활성 기능 workspace 15개·실행/초기화 최대 10개로 변경했다. 이전 준비 10개·실행 6개 설정은 대체됐다. 점검은 메인 세션 대상 3분 heartbeat, 만료·실행 횟수 제한 없음이다. 사용자 중지·권한 철회가 최우선이다.
- 고정 candidate 실행기 인계 적용 중의 신규 기능 세션 생성 금지는 중복 방지용 일시 제한이었고, 사용자 명시 요청으로 해제됐다. 아래 기준·소유권·backpressure를 만족한 준비 workspace의 신규 시작과 승인된 기존 후속은 정상 진행한다. 기존 heartbeat `5848102f`는 유지하며 새 예약을 만들지 않는다.
- 새 개발 세션 설정은 Paseo provider `paseodog`, model `openai-oauth/gpt-6.1-sol`, `thinkingOptionId: high`, `modeId: bypass`, `settings.features.fast: false`다. 실제 provider 모델 목록과 반환된 세션 설정으로 확인한다. 승인 경계는 이 문서와 COMMON 그대로이며 도구 실행 모드가 추가 권한을 부여하지 않는다.
- 사용자 최신 명시 설정은 통합 메인만 `settings.features.fast=true`, 개발 세션은 `settings.features.fast=false`다. 개발 세션 준비·보충·생성과 기존 세션의 승인된 재개에서도 `false`를 명시하고 반환 설정을 확인한다. 이는 최적화만으로 실행 설정을 바꾸지 않는 제한의 명시 예외이며 모델·thinking·mode는 변경하지 않는다. 설정은 다음 턴부터 적용되므로 현재 턴·진행 중 검사를 중단하거나 재시작하지 않는다.
- 세션 상태는 각 README 행의 정확한 cwd로 조회한다. 무필터 `list_agents`가 호출자 workspace만 반환할 수 있으므로 그 결과를 전체 목록으로 취급하지 않는다. archived 세션도 포함해 미시작과 종료를 구분한다.
- 미시작 판정은 workspace 경로·브랜치·기준 SHA 일치, 세션 이력 없음, 정확한 `RESULT-NN.md` 없음, tracked/untracked clean을 모두 만족해야 한다. `create_agent`는 정확한 workspace ID와 완료 알림을 지정해 한 번만 호출한다. 생성 응답이 유실되면 먼저 그 cwd의 세션 이력을 다시 확인하고 중복 생성하지 않는다.
- 같은 저장소의 workspace 생성·agent 시작·재개·archive와 label 변경은 Git 공통 admission 메타데이터를 공유하므로 병렬 호출하지 않고 하나씩 끝낸다. 기능 구현은 별도 worktree에서 병렬로 유지한다. 실제 `mixdog-workspace-admission.json.lock` 2초 대기 오류가 관측됐으며, 이는 코드 merge 충돌과 다르다.
- admission lock timeout 때 lock 파일 삭제·보유 프로세스 kill·설치 엔진 직접 수정으로 우회하지 않는다. 접수 여부를 상태·세션 이력으로 먼저 확인하고 원래 실행을 중복 시작하지 않는다. 순차 관리 호출은 경합 완화일 뿐, 엔진의 고정 timeout과 모든 세션 간 경합을 해결했다고 주장하지 않는다.
- 첫 메시지는 ENTRY·COMMON·번호 문서를 정본으로 지정하고, 번호 문서의 사용자 흐름·소유 경로·완료 조건과 로컬 커밋 권한을 전달한다. 다른 기능·checkout은 수정하지 않고 RESULT와 관련 커밋을 남겨 종료한다. 기능 세션은 재위임·merge·TODO 체크·workspace 정리를 하지 않는다.
- 작업 완료 알림은 빠른 깨우기 수단이고 heartbeat가 누락을 복구한다. 알림만으로 성공·완료를 판정하지 않고 상태·인계·commit·clean을 다시 확인한다. running/initializing·승인 대기·취소 상태는 자동 재실행·중단·메시지 전송하지 않는다. 미커밋 변경도 임의 인수하지 않는다. 사용자 승인한 제공자 시스템 오류의 기존 세션 재개만 아래 예외를 따른다.
- 메인에는 하나의 heartbeat만 유지한다. 같은 이름·대상으로 `create_heartbeat`하면 기존 예약을 갱신하므로 만료·횟수 인자를 생략해 무기한으로 만든다. 예약기는 메인 실행 중 새 실행을 거절하므로 중복 통합을 시작하지 않는다. 메인 세션을 archive하면 감시도 끝나므로 자동 운영 중 archive하지 않는다.
- MCP의 `list_schedules`·`inspect_schedule`는 new-agent 예약만 대상으로 하므로 heartbeat가 목록에 없거나 `Schedule not found`여도 삭제됐다고 판단하지 않는다. heartbeat 응답의 target/status/nextRunAt/expiresAt/maxRuns와 실제 메인 재진입을 확인한다.
- 완료 작업의 1~5단계를 마친 뒤 실행 슬롯과 backlog를 다시 확인해 미시작 기존 workspace와 새 보충 workspace를 한도 안에서 순차 시작한다. 진행 중인 workspace의 기준·소유 범위는 바꾸지 않는다. TODO가 소진됐거나 남은 후보가 승인·외부 환경·소유권 충돌로 막혔다면 개수를 억지로 채우지 않고 대기하며 이유를 보고한다.
- 무한 반복은 기존 미완료 TODO를 계속 처리한다는 뜻이다. 새 기능을 임의 발명하거나 같은 항목을 반복 생성하지 않는다. 검증 실패 작업은 보존하고 독립 작업만 계속한다. push·배포·의존성 추가/업그레이드·강제 삭제·브랜치 삭제·운영 서비스 변경은 승인 범위 밖이다.

## 제공자 시스템 오류의 자동 재시도
사용자는 `An error occurred while processing your request. You can retry your request` 형태의 제공자 오류에서 기존 기능 세션의 자동 재개를 승인했다. 기능 세션당 한 번만 자동 재시도하며 재실패는 보존·보고한다. 취소·권한 거부/대기·검사 실패·quota/인증 오류·메인 통합 실패를 이 예외로 우회하지 않는다.
1. 정확한 agent ID의 상태가 error이고 activeTurn·pendingPermissions가 없으며 lastError가 해당 시스템 오류인지 확인한다. workspace/cwd/branch와 변경 소유권은 원래 배정과 일치해야 한다.
2. 에이전트 label `grove.autoloop.system-retry.count`가 없거나 0일 때만 예약한다. `update_agent`로 count=`1`, request-id와 state=`reserved`를 먼저 patch한다. 기존 `paseo.*` label은 보내지 않는다(서버가 관리하며 사용자 label patch는 병합된다).
3. 오류 직후 연속 재호출하지 않고 다음 3분 점검에서 기존 세션에 `paseo agent send --no-wait --json <exact-agent-id> <resume-prompt>`를 보낸다. 최초 프롬프트·현재 worktree·유효한 검사에서 이어 가고 기존 변경/commit을 보존하라고 지시한다. 새 세션을 만들지 않는다.
4. `status: sent`는 접수이지 완료가 아니다. 접수 후 retry state를 `sent`로 기록한다. 전송 응답 유실·reserved 상태에서는 새로 보내지 말고 해당 세션의 최신 사용자 메시지/실행 상태로 접수를 판별한다. 성공·error 알림과 heartbeat로 후속 상태를 확인한다.
5. 재개 후 다시 error면 같은 count를 유지하고 자동 재시도를 멈춘다. stage/commit/TODO 완료·workspace 정리 조건은 정상 작업과 같으며 오류를 통과로 숨기지 않는다.
